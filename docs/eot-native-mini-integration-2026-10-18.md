# mini 原生接入与 FireRed + D3 配对验证

日期：2026-10-18。基线代码 `7e5ec5f`；本轮保持 D3，未发布或重启生产服务。

## 当前结论

**mini 可以作为可配置的原生音频 EOT 接入，但本轮不建议把生产 FireRed 替换成 mini。** 接口、取消和提交边界可以保持清晰；产品回放没有证明替换后体验更好。下一步应优先明确“完整请求”的产品边界，再在同一误截断预算下选择模型和工作点。

这修正了前一轮“mini 优先集成候选”的工程假设：优先集成已经完成，集成候选不等于上线胜出。

## 实现与职责

| 层 | 本轮实现 | 边界 |
|---|---|---|
| VAD | 保留 FireRed pVAD | 语音活动和短暂停顿，不判用户意图 |
| EOT | `firered` / `livekit_mini` 配置选择 | FireRed 看文本；mini 使用 LiveKit 原生音频流 |
| 意图 | 保留现有 D3 配置 | 当前负责输出期间的 keep / stop / reply / wait；空闲普通请求不调用它 |
| 请求提交 | 复用 Channel 的候选、取消和播放收尾屏障 | mini 分数不能越过未完成的意图处理，也不能直接提交请求 |
| 客户端 | 播放状态作为被动回显 | 回显不授予提交或打断权限 |

mini 复用 LiveKit 1.7.1 / local-inference 0.2.7 的模型、重采样、音频缓冲和推理触发。未增加第二个音频队列、第二个提交协调器、FireRed 隐性后备或额外串行语义模型。SDK 自带的取消/关闭默认概率不会被当作真实完成证据；模型超时或无有效结果时保守走长端点等待，并继续遵守现有语义屏障。

轻量适配层保留原生 streaming 协议，封装“结果可用”和“Channel 可提交”这两个不同条件。它在发起推理时绑定既有候选/生成身份，并在返回分数前复核，避免后台结果归到新候选。它复用现有播放策略配置，但不会实例化 FireRed。预热也按 provider 选择。底层原生计算已经进入线程后，取消等待不保证终止 CPU 计算；本轮未另外实现任务池或容量管理器。

默认仍为 `firered`。实验开关见 `config/overlays/eot_mini.yaml`；必须配合现有 Channel 所有的 LLM / SystemOne 意图模式和至少 200 ms 的 VAD 静音窗口。mini 阈值单独配置，默认采用 SDK 中文阈值 0.355，不能复用 FireRed 的 0.5。

## 验证设计

1. **生命周期与故障注入**：原生协议、续说/取消/关闭、迟到结果（包括 SDK 未取消但 Channel 候选已更换）、异常/超时、默认概率、会话隔离、配置加载与按 provider 预热。
2. **实际 AgentSession 编排**：相同 EOT 之外的配置，控制意图结果在 50 / 700 / 1,200 ms 返回；检查正常打断、附和、停止、模糊结果、服务不可用及分段文本修订。这里的意图结果是替身，验证编排而非 D3 分类质量。
3. **冻结录音回放**：真实 FireRed VAD、真实 EOT、真实 D3、实际 Channel / LiveKit；ASR 文本与到达时刻、回答及 TTS 使用替身。两个停顿用例在停顿期间提供第一段文本，避免“没有文本所以没有提前提交”的假通过。
4. **host 配对**：从 Mac 与 Pi5 实际 host settings 提取 turn policy，确认相同；仅改变 EOT provider。固定 VAD 500 ms、端点 250 ms / 3 s、D3 2,500 ms 请求预算，加入周期性被动播放状态回显，正反顺序各跑一遍。
5. **原生分数核对**：五类冻结音频分别抽取八个输入，将适配层输出与 SDK 底层原生模型的同一音频快照比较。

最初的默认策略探路回放与后续实际 host 策略回放分别保存。下面产品结论只使用 `product-policy-replay.json`。两端均在隔离进程测试；Pi5 使用 `/var/tmp/eidolon-mini-integration-20261018`，生产服务保持运行。

## 结果

每台 host 的最终回放为 7 个场景 × 2 个 EOT × 2 次正反顺序，共 28 次；两端共 56 次。均无运行异常。每个场景中两次的提交数量、D3 意图和旧播放控制结果一致。

下表的延迟为 **VAD 发出停止事件 → 用户请求正式提交**，单位 ms，取两次中位数。VAD 已等待约 500 ms；这不是“最后一个音素 → 回复”的全部延迟。只有两次重复，不据此宣称总体速度提升。

| 场景 | Mac FireRed / mini | Pi5 FireRed / mini | 行为与结论 |
|---|---:|---:|---|
| 空闲时“帮我详细介绍一下这个方案” | 378 / 2,505 | 415 / 2,505 | 都只提交一次；mini 多等约 2.1 s，明显退步 |
| 播放中“那它的主要风险是什么” | 520 / 504 | 642 / 787 | 都正确取消旧播放、提交一次；没有稳定的 mini 优势 |
| “嗯，那个……帮我查一下明天的天气” | 2,505 / 2,507 | 2,504 / 2,504 | 均合并成一次请求，最终仍走长等待；没有调用天气工具 |
| 完整句、长停顿、继续补充 | 首次 336 / 308 | 首次 329 / 321 | 四组均提交两次；按一次完整提交的场景预期，均未达标 |
| 播放中“嗯” | 不提交 / 不提交 | 不提交 / 不提交 | D3 均为 keep，旧播放继续 |
| 播放中“别说了” | 不提交 / 不提交 | 不提交 / 不提交 | D3 均为 stop，旧播放中断，没有新回答 |
| 播放中“等一秒” | 不提交 / 不提交 | 不提交 / 不提交 | D3 均为 stop；不是持久等待或定时恢复 |

首个可听 PCM 的相同口径：普通介绍请求 Mac 为 **394 / 2,521 ms**、Pi5 为 **457 / 2,535 ms**；播放中追问 Mac 为 **535 / 520 ms**、Pi5 为 **678 / 815 ms**。这里的回答与 TTS 是替身，主要用于检查提交之后的输出链路。

补充的 40 个原生分数核对样本中，mini 推理中位数为 Mac 6.5 ms、Pi5 93.9 ms。这与上表的正式提交等待是不同指标，不能用推理更快代替接话体验结论。

真实 D3 在最终回放中每端调用 16 次。按 EOT 分组的调用中位数，Mac 为 132 / 131 ms，Pi5 为 190 / 191 ms；Pi5 存在网络/服务延迟波动，不能把追问场景的全部差异归因给 EOT。

- 原生分数核对：Mac / Pi5 各 40 个输入全部通过，适配层与同机直接模型分数误差小于 `1e-6`，且都有真实推理记录。40 个输入在两台 host 的 0.355 阈值决策一致，最大分数差约 `3.49e-6`。
- 首轮时序矩阵：每端 36 个场景通过，覆盖两个 intent provider 配置、三类意图、三种返回时机、两种 EOT。
- 最终配置、会话隔离、预热、取消及已有相关回归：每端 89 项通过。
- 模糊/超时/错误意图与分段文本修订：每端 14 项通过。

候选快照加固后，每端重跑了涉及 mini 的 25 项场景测试，并对普通请求、播放中追问、犹豫续说和长停顿补充各做 FireRed / mini 回放，共每端 8 次；均无异常，提交数量与原结论一致。最终运行代码、配置开关及测试文件的两端哈希一致。

以上共 **每端 139 项不同测试**，未把重复执行的测试累计为新增覆盖。产品场景的拆轮和迟答问题单独保留，不因运行没有异常或单元测试通过而算作体验验收通过。

## 对产品边界的判断

- **完整句迟答**：mini 把“帮我详细介绍一下这个方案”送入长等待，在两个 host 都复现。相同录音的分数约 0.23，低于 SDK 中文阈值；这不是 D3 慢，因为该空闲请求没有调用 D3。
- **犹豫起句**：两者均能保留前缀并合并后续文本，但最终仍可能进入长等待。模型接入没有自动解决最终接话延迟。
- **完整句 + 长停顿 + 补充**：按该用例“一次完整提交”的期望，两者均拆成两轮。第一句本身可独立成立，录音中还存在约两秒低能量间隔，因此不能从这个结果推出“所有此类停顿都必须等待”；需要先确定产品希望接话、短回应还是继续听。单纯拉长全局静音时间会牺牲其他请求的响应速度。
- **“等一秒”**：本轮 D3 把它判为 stop，两种 EOT 都只停止旧播放。没有验证出“自动等一秒后继续”的能力，也没有新增持久等待状态。这属于既有意图/交互语义边界，不应误归因给 EOT 模型。

因此，**结束证据、交互意图、完整请求提交不是同一个判断**。本轮的 D3 仍只处理输出期间的意图；替换 mini 不会凭空让空闲状态获得“继续听 / 可以回应 / 明确等待”的语义判断。

## 后续方案与验收门槛

| 顺序 | 工作 | 验收方式 |
|---|---|---|
| 1 | 明确空闲请求、输出中打断、显式等待、句内停顿、完整句后的补充各自规则 | 冻结带上下文的产品标注集；争议样本单列，不靠模型分数决定标签 |
| 2 | 在既有 Channel 提交所有权中验证这些规则 | 保留候选身份、文本版本、续说取消和旧播放完成约束；工具/业务副作用只允许在正式提交后发生 |
| 3 | 对单主模型做阈值与时序校准 | 调参集与保留集分离，在同等误截断预算下比较最终等待与超时率，不能为本轮几个句子定制阈值 |
| 4 | 需要时再将 TurnSense 1.0 作为独立候选比较 | 同一数据、同一边界、同一预算；没有收益就不增加长期级联 |
| 5 | 获胜配置做真实 ASR、RTC 与 BOX-3 验收 | Mac/Pi5 均测连续对话、停顿续说、取消后新请求、并发与资源压力，再决定发布 |

**host 选择**：目前没有依据让 Mac / Pi5 使用不同语义方案或不同 EOT 模型。两端继续 FireRed + D3；mini 留作同接口实验候选。并发数、预热与内存预算可以按硬件能力区别配置，但本轮单会话回放不能替代容量验收。

## 证据与限制

完整实验目录：`/Users/manson/ai/eidolon/diagnostics/2026-10-18-mini-integration/`。其中包含部署策略快照、源码哈希、回放脚本、原生分数核对、每个 host 的逐条结果和测试日志。音频沿用上一轮冻结语料及其哈希清单。

这里没有进行新的 BOX-3 麦克风、扬声器、AEC、真实 ASR 或真实 Agent 工具副作用测试。首声是测试 AudioOutput 收到可听 PCM 的时间，不是设备扬声器发声时间；回答内容由替身生成，不能据此宣称 Agent 回答质量提升。每个产品场景两次重复用于核实行为，不足以推断线上总体错误率或时延分位数。

实现依据是安装版本的原生 API 与生命周期，官方参考：[Turn handling](https://docs.livekit.io/reference/agents/turn-handling-options/)、[TurnDetector](https://docs.livekit.io/reference/python/livekit/agents/inference/eot/detector.html)。
