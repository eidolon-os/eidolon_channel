# 意图识别模型替换验证：评审报告

日期：2026-10-17。范围：当前 DS Flash 意图分类器与 pplx / d3 的可替换性；不更换 FireRed EOT，不开启 mini，不修改生产状态机或配置。隔离 HTTP 适配器及实验保存在 diagnostics。

## 评审结论

**d3 是优先替换候选，但不能采用“换接口 + 概率低于 0.8 就当 UNCERTAIN”的方式直接上线。** 它在本轮新测试集中接近 DS 的标签结果，耗时显著降低；实际接入同时证明，阈值、错误回退和调用范围会直接改变产品行为。pplx 可保留为对照，不默认作为每次低置信请求的第二跳。

需要分别 review 两件事：

1. **四标签兼容替换**：保持当前 keep / stop / reply / wait 语义与调用位置，只更换证据提供者。本轮已经验证协议、分类、实际策略动作与 SDK 接入。
2. **完整请求的六状态能力**：明确等待、未说完、解除等待等。当前四标签及调用范围不能完整表达；换一个更快模型不会自动获得这些能力。相关失败单列，不混入四标签模型准确率。

最终不把“所有逻辑都没有遗漏”作为可证明结论；下文逐项列出已执行验证、反例及未覆盖范围。生产发布仍需关闭明确的阻塞项。

## 1. 验证设计与基线

| 边界 | 要验证的问题 | 本轮方法 |
|---|---|---|
| 任务契约 | 替换后究竟判断什么，四标签与六状态是否混用 | 复用当前分类说明；六状态需求另列 |
| 输入 | 上文、引用、否定、改口、ASR 噪声、缺业务参数是否误导 | 冻结文本集、上下文对照、长输入探针 |
| 输出 | choice 与概率是否合法，分数能否直接当授权 | 严格解析、异常响应注入、真实概率与动作回放 |
| 调用范围 | 普通话轮、打断、无注意力、禁用打断由谁触发 | 真实触发门测试及无旧播放 SDK 探针 |
| 时序 | interim/final、重复 final、修订、代次切换、旧回答更换 | 实际 handler、HTTP 适配器故障注入和 SDK 回归 |
| 取消/超时 | 排队是否计时、取消是否释放容量、迟到是否越权 | cooperative 与 non-cooperative 分开测 |
| 动作 | 恢复、停止、接话是否正确；是否重复提交 | 真实 TurnPolicyRuntime 回放和 AgentSession 观察 |
| 服务 | 4xx/5xx、断连、非法 JSON、限流、排队、长输入 | 本地故障注入 + 两端真实服务小规模负载 |
| host | 同输入是否同结果，公网延迟是否不同 | Mac/Pi5 同集对照 |
| 基线一致性 | 是否把不同超时参数误当模型差异 | 区分默认 1.5 s 压力轮与生产 2.5 s 完整策略轮 |

生产基线：Mac Channel `a3dc0f6`，Pi5 为 `pi5-playout-finalization-20261016-1`；EOT 保持 FireRed。当前分类器位于 `intent_classifier.py`，使用 `LlmInterruptClassifier._INSTRUCTIONS`，只输入正在播放的文本末尾 2,000 字符及用户文本。新适配器保留这个边界。

SystemOne 的请求格式不同，额外需要 choice criteria；因此这是同一分类语义下的服务替换比较，不是逐 token 完全相同的模型权重实验。测试只使用自编文本，没有上传实际用户会话。

初轮 SDK 使用辅助代码默认 `intent_timeout_ms=1500`。发现与生产不符后保留原始结果，并以两端相同的完整脱敏生产策略重跑，包含 `intent_timeout_ms=2500`、VAD 500 ms 等参数。初轮不得作为生产时序基线，修正后的记录文件为 `*-sdk-baseline.jsonl`。

每个模型在 Mac 同轮测试；Pi5 同集验证两个远端 decider。此表全部请求成功，含连接、网络和排队，不含 ASR、回答生成及播放。DS 是本轮重跑的当前四标签基线，不是上一轮六状态结果。

| 模型 | Mac 匹配数 | Mac p50 / p95 | Pi5 匹配数 | Pi5 p50 / p95 |
|---|---:|---:|---:|---:|
| DS Flash | 72/72 | 1,036 / 1,258 ms | 本轮未从 Pi5 直接测 DS | — |
| pplx | 69/72 | 143 / 207 ms | 69/72 | 125 / 183 ms |
| d3 | 71/72 | 105 / 174 ms | 71/72 | 99 / 129 ms |

两端 decider 错误标签一致。pplx 三个差异都出现在“不确定表达”组；d3 一个差异也在该组。d3 将“算了，我还不知道怎么表达。”标为 stop（0.453），标注为 wait。两者在其余本轮主要类别表现较好，但每组仅六条左右，不足以认证泛化。

### 概率门槛必须通过动作验收

预先定义的校准规则：在 `[0, .5, .6, .7, .8, .9, .95, 1]` 网格中，选择校准集零错误接受时覆盖最大的门槛。两个模型在简单校准集上都是 24/24，规则选中 0；它在更复杂测试集产生错误。这说明本次校准样本不能支撑上线门槛，不能事后利用测试集改选“最优值”。

另保留服务文档已有的固定 0.8 对照：

| 模型 / 门槛 | 接受数 | 接受中的标签错误 | 正确但被拒判 |
|---|---:|---:|---:|
| pplx / 0 | 72/72 | 3 | 0 |
| pplx / 0.8 | 63/72 | 0 | 6 |
| d3 / 0 | 72/72 | 1 | 0 |
| d3 / 0.8 | 67/72 | 0 | 4 |

拒判没有计为正确预测。当前代码的 UNCERTAIN 在用户不再说话时会走 ROLLBACK，恢复旧播放，并不是一直保持安静。因此“拒判更保守”并不普遍成立。

在同一真实 `TurnPolicyRuntime` 上按 VAD 开/关、EOT 0/0.99 回放（每样例四种状态），pplx 0.8 仍有四个动作差异，来自一个本来正确的 reply 被拒判；d3 0.8 在这 72 条上无动作差异。动作矩阵是同样例状态扩展，不是额外独立样本。

**随后 SDK 集成给出了 d3 的反例：**同一上下文中，“他说‘别说了’是什么意思？”原始结果是 reply，最大概率 0.703。无门槛时新回答调用 1 次；0.8 门槛时映射成 UNCERTAIN，旧播放未取消，新回答调用 0 次。两次都调用真实 d3，使用实际 AgentSession。不能用测试集“接受区零错”覆盖这个真实漏答。

## 4. 协议、生命周期与故障验证

两端各 **85 项通过**：60 项隔离适配器/真实 handler 测试，加 25 项现有异步所有权与触发门测试。新增测试覆盖：

- 四标签映射、d3 必须指定 model、上文截断、用户文本与指令分离。
- 缺失字段、错误 type、未知/额外选项、非数值/布尔/NaN/Infinity、概率越界/和错误、choice 非最大概率。
- HTTP 400/401/404/413/429/500/503/302、非 JSON、连接异常；不跟随重定向、不隐式重试、不伪造 ready。
- 排队计入超时、取消释放并发槽、关闭后拒绝新请求、两会话结果不串扰。
- 4 标签 × 高低概率 × VAD 开关的实际动作；异常经过真实 handler 后的现有回退动作。
- 文本修订、generation、旧回答更换、已完成候选的迟到 HTTP 结果；重复 final 只调用一次；端点等待取消不取消共享意图任务。

另运行完整 `test_interrupt_model_timing.py`：Mac / Pi5 均 **46 passed**，各约 245 / 259 s。连同上述测试每端共 131 项通过；后面的独立 deadline 与 A→B→A 故障探针均失败，未包含在这 131 项中。该组覆盖生产 SDK 的模型早/晚到达、续说、显式抢占、PCM 恢复与消息提交。新适配器的 mock HTTP 故障测试与已有 SDK 时序回归是互补证据，不能称为每种故障都已穿透物理设备链路。

### 发现：取消不合作时，deadline 仍可能失效

独立故障探针设置 handler 预算 20 ms，模拟 provider 捕获取消后继续返回 stop。Mac 约 53 ms、Pi5 约 52 ms 后，实际 handler 仍接受结果并执行 CANCEL。

这是**失败项**：当前代码有候选/文本有效性检查，但没有在接受结果前再次校验绝对截止时间。普通 httpx 取消测试通过，不代表所有 provider 都合作；本次没有声称真实 d3 会忽略取消。该缺口属于现有协调器，DS 也经过同一位置。若未来收紧延迟预算，必须补绝对 deadline fence，不能只依赖 task.cancel。

### 发现：A→B→A 修订可让已失效请求重新取得所有权

第二个独立故障探针保持同一候选/播放身份，将转写 A 改为 B，再改回 A；模拟第一次请求忽略取消，新请求读取了更新后的 assistant_text。旧请求返回 stop 时，新请求仍在等待。两端真实 handler 均接受旧结果并执行 CANCEL。

原因是当前 key 仅比较 scope 和文本；回到 A 后旧 key 又等于当前 key，没有请求实例或单调修订号约束。该故障注入证明单向 A→B 测试通过不足以覆盖修订回退，不代表真实 d3 已发生过该事件。应在证据身份中使用已有单调修订信息或当前请求身份，保证失效不可逆；不要为此建立第二套产品话轮状态机。

## 5. 实际 AgentSession 的产品边界

采用真实 Channel / LiveKit / FireRed，意图分类调用真实服务。STT、回答 LLM、TTS 使用脚本替身，音频为合成输入；无 RTC、扬声器、AEC 或真实业务工具。每轮观察到首音频后 6.2 s，记录旧 SpeechHandle 是否中断、新回答调用数和提交消息。它验证编排，不代表可听延迟或物理音质。

生产策略轮分别覆盖 keep、stop、改述请求、引用问题、明确等待、未完成表达、不确定表达和解除等待文本。原始结果与失败都保留；服务恢复后的复核不覆盖旧记录。

修正后的生产策略轮共 **40 个场景运行**：Mac 三模型各 8 个、Pi5 两个 decider 各 8 个。两端 pplx/d3 没有 HTTP 错误；附和和停止均不产生新回答，两条正常接话问题均各产生 1 条用户消息、1 次回答调用。DS 在 Mac 的一个改述请求上耗尽 2.5 s 预算，分类等待被取消，旧播放恢复而未接话；其他独立复核中同一 DS 请求成功。基线也有网络/时延失败，不能将所有漏答都归因于替换。

| 场景 | 要求 | 已发现的边界 |
|---|---|---|
| 附和 | 旧播放继续，不开启新回答 | 正常服务结果下成立 |
| 明确停止 | 停旧播放，不开启新回答 | 正常服务结果下成立 |
| 新请求 / 引用问题 | 停旧播放，只提交一次新请求 | 正常回复结果下成立；超时/错误/拒判可使请求被漏掉 |
| 明确等待 | 暂时安静，保持等待状态 | 多个模型判 stop 可在当前轮安静，但没有证明存在持续等待状态 |
| “不是，我的意思是……” | 让出声音，等待表达完成 | 多个模型返回 wait/UNCERTAIN，现有策略会恢复旧播放；属于既有边界缺口 |
| “现在请回答” | 结合真正等待状态决定继续/新回答 | pplx/d3 与 DS 出现 keep/reply 差异；此探针没有建立前一轮真实等待状态，不能据此宣布谁正确 |
| 普通轮次中的明确等待 | 仍应阻止新回答 | 实测无旧播放时分类器调用为 0，仍触发回答；单换分类模型无法覆盖 |

普通轮次探针在 Mac/Pi5 上均验证 d3 调用 0；Mac 还以 DS 基线复核。正常问题和“先别回答，我还要补充”均进入回答。原因是现有 `evaluate_semantic_interrupt_gate` 要求有旧播放或打断窗口。此项是**基线调用范围缺口，不是 d3 引入的回归**。

初轮 d3 曾出现 Mac 3 次、Pi5 4 次 SDK HTTP 错误；同时间产品边界请求也有失败。首次记录只包含 HTTPStatusError，未保存状态码，不能确认具体 4xx/5xx 或服务端根因。原样输入随后独立复核成功，修正观测代码后保留 HTTP 状态与错误正文。不能用恢复成功宣布之前的服务错误不存在。

## 6. 负载、上下文与 host

每端、每模型分别做 4 次串行和 4 批四并发请求。短输入均成功；四并发大部分响应约 pplx 410 ms、d3 260 ms，而不是固定 100 ms。这里最多是少量并发突发，不是长时间容量或 SLA 验证；两台主机也可能同时访问同一后端。

长上文约 1,500 input tokens 时，pplx 约 397 ms、d3 约 242 ms；长用户文本约 1,570 tokens 时分别约 450 ms、255 ms。上下文越长成本越高，输入应保持必要且结构化。

10,000 个“测”的边界输入：pplx 两端均触发客户端 2.5 s 超时；d3 两端返回，usage 报告 10,360 input tokens，约 1.4 s。这与文档“超过 8K 报错”的描述不完全一致。不能假定两服务的长度上限和错误行为完全相同；上线前需要版本化的输入限制契约，不能用字符数冒充精确 token 数。

Mac/Pi5 调用的是远端同一模型服务，无需在 Pi5 部署 27B 权重。当前数据支持统一模型选择、分别测量网络路径；不支持按 host 名称分成不同意图逻辑。新适配器当前的并发限制是每实例限制，不是已实现的 host 全局预算。

## 7. 发布前的具体决策

| 项目 | 决策 |
|---|---|
| 首选模型 | d3 继续影子验证；pplx 保留质量与可用性对照 |
| 是否直接上线 | 不建议；概率拒判动作、服务故障与输入契约尚未闭合 |
| 是否采用固定 0.8 | 不采用；已复现正确 reply 被过滤并导致漏答 |
| 是否照搬校准集选出的 0 | 不采用为长期结论；简单校准集没有代表实际困难样例 |
| 是否默认失败后串行调用 DS/pplx | 不默认引入；会增加尾延迟，也没有解决状态语义缺口 |
| 超时配置 | 保持生产基线用于比较；后续依据排队/网络 p95 与故障动作联合选择 |
| 六状态 | 需要单独的 Channel 状态契约，不能伪装为 provider 参数替换 |

接下来应关闭四个具体问题：

1. **低置信动作契约**：区分“已确认附和”和“尚未判断出来”，不要因为两者都暂时没有新回答就一律恢复旧播放。用独立校准集联合选择阈值、拒判覆盖与最终动作。
2. **服务失败契约**：完整记录状态码、request timing、重试/取消原因，验证网络错误时允许的恢复动作与会话活性；不得把 unavailable 当成 keep。
3. **异步结果有效性**：接受结果前校验绝对 deadline、候选身份及单调修订/请求身份；超时与失效都不可因文本恢复原值而重新生效。
4. **明确范围**：若本次只替换打断分类器，就按四标签兼容门槛验收；若要解决普通请求“先别回答”，必须扩展触发范围及持续等待状态，作为独立行为变更验收。

## 8. 尚未证明的事情

- 没有独立真人多轮数据、多人盲评或充分语言/口音分布；语音识别错误仅用文本模拟。
- 没有物理 BOX3、真实 AEC/RTC 网络、设备可听首音延迟和真实 Agent 工具副作用测试。
- 没有持续高负载/长连接长时间稳定性、服务端队列及首次 HTTP 错误的根因定位。
- 没有实现新的六状态产品策略，也没有证明等待解除、多轮等待期间的所有恢复行为。
- 适配器未注册进生产工厂/配置，未验证完整启动预热、Ops 灰度、回滚部署。当前现有工厂只构造 LLM provider，需要正式实现后再验收这些入口。
