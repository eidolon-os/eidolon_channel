# EOT 工作点与接话体验复核

日期：2026-10-18。代码基线：Channel `aa86d2d`。固定现有架构和 D3，未修改生产代码、模型配置或重启服务。Agent 问题由独立任务处理。

后续更新：本报告保留修复前的比较证据；其中候选对齐缺口现已完成代码修复和两端回归，见 [对齐修复与最终验证](eot-transcript-alignment-2026-10-18.md)。模型推荐仍为 FireRed + D3。

## 结论

**Mac / Pi5 继续保留 FireRed + D3。mini 默认阈值存在可重复的完整句迟答；降到 0.20 只能改善部分样例，并在受控 ASR 延迟路径暴露提交文本缺失，不能据此上线。** 自然长停顿后的两次提交不再判为失败，也不以新增“业务请求完整性判断”作为优化前提。

这次选择依据是“提交内容正确之后，接话是否及时”，不是追求提交次数最少。原有 VAD、单主 EOT、输出期间 D3、Channel 唯一提交入口的分工继续保留，不增加双模型级联或新的语义状态机。

五类完整请求每端每配置 10 次：FireRed 的 ≥2 s 等待为 **0/10**，mini 默认为 **4/10**，mini 0.20 为 **2/10**。这是选定诊断集的计数，不是线上迟答率。

## 2. 续说与控制：检查文本，而非只数提交

| 场景 | FireRed 基线 | mini 默认 | mini 0.20 | 判断 |
|---|---|---|---|---|
| 嗯，那个……帮我查一下明天的天气 | 一次提交，包含完整请求 | 一次提交，包含完整请求 | 一次提交，但只有“嗯，那个。” | 0.20 的“快”不能算收益；两端各两次复现 |
| 完整句、长停顿、继续补充 | 两条完整文本、两次提交 | 两条完整文本、两次提交 | 两条完整文本、两次提交 | 允许自然拆轮；不据此判失败，也未评价 Agent 理解 |
| 播放中“别说了” | 停止旧输出，无新提交 | 同左 | 同左 | 本轮控制结果一致 |
| 播放中“嗯” | 保留旧输出，无新提交 | 同左 | 同左 | 本轮控制结果一致 |
| 单独“我觉得” | 长等待后提交 | 同左 | 同左 | 没有后续音频，不把这个用例当作已观察到的抢话 |

主回放无运行异常、D3 调用无记录到的错误。但“运行成功”不等于文本正确，0.20 的天气续说属于未通过的功能场景。

### 时序定位

追加 FireRed / mini 0.20 对照，固定最终文本的到达时刻，只比较“只有 final”与“提前 800 ms 有 partial interim”。两端现象一致：

| ASR 时序 | FireRed 提交文本 | mini 0.20 提交文本 |
|---|---|---|
| final 延迟到达 | 嗯，那个。帮我查一下明天的天气。 | 嗯，那个。 |
| 同一 final 时刻，提前有“帮我查一下” interim | 嗯，那个。帮我查一下明天的天气。 | 帮我查一下嗯，那个。 |

mini 0.20 的正式文本发布发生在天气 final 到达前约 **341–344 ms**。记录显示：旧 framework 前缀进入文本 settlement 时被判为 `interim_only_candidate`，随后正式发布；后到 final 虽被 STT 入口接收，但没有形成新的正式提交。加入 partial interim 还出现了拼接顺序不正确。

这确认的是**现有音频 EOT 接入与文本候选对齐的时序缺口**，不是 Agent 历史问题，也不是“用户必须一次讲完”的问题。证据尚未完整归因到 SDK、候选生命周期或具体修复点，因此本轮不做猜测性补丁，不把它宣称为 mini 权重本身导致丢字。后续如推进音频 EOT，必须先在既有提交/文本 settlement 契约内通过这类回归；不需要新增业务语义门控。

### 后续补充：候选生命周期定位

又增加 **8 次**生命周期记录回放（每端 FireRed / mini 0.20 × 有无 interim），不是计入前述 152 次的重复统计。两端再次复现相同文本结果。新证据确认：续说超过 800 ms merge grace 后，Channel 替换了仍未提交的候选；framework 仍保留旧前缀。mini 的音频结束先于新 final，旧前缀进入只含 interim 或完全无文本的新候选，`interim_only_candidate` 放行后发生错误拼接/提交。后到 final 遇到 committed 候选，未形成新发布。

因此，修复对象已收敛到**候选生命周期、framework 文本归属和既有 settlement 的覆盖检查**；不是业务完整性判断，也不能只把“等待 final”作为全局规则。Mac 既有相关测试 85 项通过，但未覆盖这条跨候选组合路径。此轮只做定位，尚未修改运行时代码。完整证据与后续验证契约见 [候选对齐定位](../../diagnostics/2026-10-18-eot-alignment/README.md)。

## 4. 实际 ASR 复核与事件回放

两端实际配置均为 Bailian。本轮 Pi5 **4/4** 返回非空 final，Mac **0/4** 在观察窗口内获得非空 final，日志记录到一次连接超时（15 s）。因此不能宣称两端真实 ASR 的完整链路验收通过，也不能把 Mac 连通性问题算到 EOT 模型性能中。

Pi5 的关键结果：

- “介绍方案” final 在音频开始后约 2,599 ms 到达；“多久能做完”约 2,305 ms。
- 犹豫起句被识别为“あ。”、“那个。”，完整天气请求 final 约 5,000 ms 到达；包含 6 个 interim。这里已经出现与参考文本不同的 ASR 内容。
- 长停顿补充的两个 final 分别约 2,592 / 6,798 ms 到达，文本均正确。

把这批实际文本与到达时间固定后，在 Mac / Pi5 各做 12 次额外回放；两端提交内容和次数一致：

| 场景 | FireRed | mini 默认 | mini 0.20 |
|---|---|---|---|
| 介绍方案 | 完整提交；VAD 后约 3 / 9 ms | 完整提交，但约 2,507 / 2,503 ms | 完整提交；约 3 / 3 ms |
| 多久能做完 | 完整提交；约 142 / 156 ms | 完整提交；约 131 / 133 ms | 完整提交；约 136 / 132 ms |
| 犹豫后天气请求 | 先提交“あ。那个。”，随后提交完整天气请求 | 合并为一次，保留天气请求，约 2.5 s 等待 | 合并为一次，保留天气请求，VAD 后快速提交 |
| 完整句后长停顿补充 | 两段文本、两次提交 | 同左 | 同左 |

每格时延仍为 Mac / Pi5、VAD 事件到提交，单次测量。几毫秒意味着 ASR 和部分端点等待已经在 VAD 确认前完成，**不是总体接话延迟只有几毫秒**。录制回放保留文本和时间，没有捕获提供商的 revision 元数据，也没有把实时网络重新接进 AgentSession，因此不等同于真实设备全链路。

这是对主实验的重要补充：**0.20 的后半句缺失依赖特定文本到达时序，不是所有天气请求都会漏；FireRed 在实际 ASR 将犹豫词识别成异语文本时，也有前缀提前提交。** 第一条前缀并非完整业务请求，与前述“完整句后的自然补充”应分开评价。回答仍是 MockLLM，不能据此断言实际 Agent 会说什么或用户一定听到了抢话。

因此，两类证据都要保留：正常到达时序下的体验与延迟/修订时序下的可靠性。不能只选对某个模型有利的那一类。

## 5. 资源、host 与架构选择

主回放 20 次 / 配置 / host 的进程 CPU 核当量中位数，FireRed 为 Mac **0.131** / Pi5 **0.152**；mini 默认 **0.118 / 0.161**；mini 0.20 **0.109 / 0.164**。各配置单次实验事件循环延迟 p95 的中位数都约 Mac **1.2 ms** / Pi5 **1.1 ms**，观察到的最大延迟分别在约 20–23 / 51–54 ms 范围。

这些指标包含测试 harness、模拟 STT/TTS 和实际 VAD，不是单独 EOT 成本；没有多会话压力或生产容量验收，不依据小差异宣称资源胜出。此前独立模型/线程/内存结果仍见 [系统评估](eot-system-evaluation-2026-10-17.md)。本轮两端的关键功能结果一致，**没有支持 Mac / Pi5 改用不同语义策略或不同 EOT 模型的新证据**。

| 选择 | 当前建议 | 理由 |
|---|---|---|
| 可部署基线 | 两端继续 FireRed + D3 | 已有生产验证；本轮未证明新组合整体更优，不代表 FireRed 没有缺点 |
| mini 默认 | 保留实验配置 | 原生集成可用，但完整句迟答仍复现 |
| mini 0.20 | 不发布 | 部分正常样例更快，但延迟/修订时序存在错误提交；片段分类也显示激进取舍 |
| TurnSense 1.0 | 保留下一候选 | 中文片段结果较好；尚未通过同等运行时和时序验证，不能直接宣布优于 FireRed |
| 双模型级联 / 额外语义 LLM | 不新增 | 本轮没有收益证据；增加复杂度也不直接解决文本版本对齐 |
| “完整请求提交策略” | 不作为独立扩建项目 | EOT 判断接话时机，Channel 保证正确文本提交；业务理解属于 Agent |
