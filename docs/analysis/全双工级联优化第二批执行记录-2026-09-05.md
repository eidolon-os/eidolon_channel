# 全双工级联优化：后续实施与验证

最新进展见文末“第十七批”。前面保留历批记录，便于比较。

本批聚焦现有主链的三处逻辑问题，复用候选协调器、话轮裁决器、音频效果执行器和既有测试框架。生产代码未引入新分类器、热词表或超时阈值。

## 实施与反例

| 问题 | 修改前证据 | 本批处理 |
| --- | --- | --- |
| final 先于 VAD stop 到达，已有完整转写仍被当成等待新证据 | 三种事件顺序的生产回调链 E2E 中，只有 final 先到失败，1.5 秒观察时音频仍暂停 | VAD stop 复用同一裁决入口，用当前候选 final 与已停声事实重新判断；恢复原 SpeechHandle，完整输出剩余回答 |
| 输出暂停时并行执行两套策略，未采用的旧策略提前写分数和冷却 | 原有单一裁决契约是 strict xfail | 暂停主路径直接使用 TurnPolicyRuntime；旧 EOT 策略仅保留在实际消费其结果的 fallback，fallback 读取本次评估后的分数 |
| ASR 快速修正被节流后仍携带上一句高分 | 50ms 内旧文本 0.95，新文本未经评分却仍返回 0.95 | 缓存分数绑定评分文本；未评分的新修正清为未知值 0，重复文本复用原分数，final 绕过节流正常评分 |

候选 final 在后续不同 interim 出现时失效；已结束候选和新 generation 不能复用旧 final。没有将“所有 final”都变成提交或打断命令：现有策略仍可 HOLD，未解决的语义问题继续暴露。

## 方案反馈与剩余范围

FD-SETTLEMENT 的“低分 final 先到但不能恢复”已修复；原有单一裁决契约已转为正常测试。一般的不确定 final 仍可能进入长 HOLD，这个原有失败契约保留，不等于所有暂停截止问题都已解决。

三项双讲意图契约继续使用 strict xfail，并不计为通过：

- “好的”：应保留回答，当前误取消。
- “不要停止，请继续刚才的解释”：应保留回答，当前误取消。
- “不是，我说的是明天”：应及时接管话轮，当前未能及时打断。

完句分数不能替代意图区分。下一步仍需对上述冻结用例取得独立意图证据，再接现有 classifier/裁决接口；不能按这三句话加分支或继续调 EOT 阈值。

已核查现有 SDK 的 adaptive interruption：依赖 LiveKit Cloud 推理服务，并非自托管安装中可直接启用的本地模型。当前配置不能仅凭选项存在就认定它可用，也未切换现有 owner。[官方服务说明](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling/)。本批先完成无需该外部依赖的确定性修正。

## 第三批：端点契约、过期 final 与真实意图实验

本批补齐两处既有链路契约，生产代码仍未加入新的意图分类服务、热词表或定时器。

### 已修复

**既有端点策略没有传给 SDK。** LiveKit 不会调用 ChineseModel 的 `get_dynamic_silence_threshold()`。Agent 现在通过公开 `turn_handling.endpointing` 绑定该策略已有的快/深等待边界，默认由 SDK 的 0.5s/3.0s 变为策略本来的 0.25s/2.0s。没有调整模型阈值，没有实现另一套端点引擎。这里只传入两个边界，不宣称 SDK 实现了策略中的全部中间档位。PTT 仍由释放按键提交。

原有“显式绑定端点边界”契约已从 strict xfail 转为通过。完整短句的 1.5s 延迟契约仍未达标，现已改用生产 Agent 回调链验证，保留预期失败；绑定边界并没有修复 EOT 对所有短句的判分。

**旧 final 在 SDK 内污染已更正文本。** 同一 stream/revision 的序号 2「明天去上海。」之后到达序号 1「明天去北京。」，修改前全双工、半双工最终都提交了「明天去上海。 明天去北京。」。只修协调器最终文本不能阻止 SDK 提前接收错误版本。

现在由既有 TranscriptEvidenceBuffer 在公开 STT 节点处检查版本，过期事件在 SDK 消费前被拒绝。只有明确的 stream、revision、sequence 才参与比较；不同句段、重连流、缺少身份的数据不会被猜测为过期。相同序号的 interim → final 仍允许升级。历史最多保留 64 个最近版本身份，并随 buffer.clear 清除；这不是跨无限历史的去重承诺，也不去重正常的重复说话。

## 第四批：清理偏离项，接通语义裁决主链

本轮删除独立 `test_real_interrupt_intent.py` 实验脚本、未实现且无调用方的 ONNX 分类器占位，以及本任务生成的 22 个调试 WAV（约 4 MB）。保留历史失败 JSON 和能复现问题的生产链路测试。没有添加识别用户短语的热词表，没有另建对话引擎或供应商客户端框架。

### 主线变化

- `LlmInterruptClassifier` 复用既有 LLM 适配器，按通用语义返回保持、停止、接管或不确定。模型只处理重叠输入的 final；重复 interim 不发请求。语义标签不伪造置信度概率。
- 现有 `SemanticInterruptHandler` 异步获取证据，绑定候选、generation、SpeechHandle 和 final 文本。文本修订、换轮、换回答、关闭后，旧结果不能取消新回答。保持/不确定在停声后恢复原播报；停止不生成回复；接管进入原有话轮流程。分类超时预算 1500 ms，失败时保留并恢复原缓冲。
- E2E 发现：模型结果稍晚时，SDK 在进入完成 hook 前就因旧 SpeechHandle 不可打断而放弃新回复。现通过 SDK 公开 turn-detector 协议协调在途裁决和取消收尾；原 EOT 概率与 0.25/2.0 秒端点配置仍生效。没有从 SDK 私有入口补发回复。
- 更正、转题和普通接管共用同一“需要新回复”谓词，裁决记录与完成边界保持一致。
- 工作区 `config/settings.yaml` 已选择 `intent_provider: llm`；配置 schema 的 `none` 保留兼容路径。full duplex 非重叠输入、half duplex、PTT 不调用意图模型。没有部署到运行中的服务。

## 第五批：以停声到有效回复音频为验收方向

本轮补齐体验测量，未把功能通过率当作延迟验收。复用现有 PCM 回放、播放段、EOT 和 TurnTimeline；没有新建端点引擎或投机生成框架。

### 测量口径

- 主指标：最后一帧有声输入送入链路，到用户提交之后的新回复段首个非静音 PCM 到达内存播放端。输入按真实时间回放，20 ms 帧的 RMS 门槛为 120/32768；这是合成素材的可复现停声估计，不是人工标注或设备采集时间。尾部静音和迟到 VAD stop 不会让结果显得更快。
- 辅指标：最终被提交的同一文本，其 final EOT 达到完成阈值，到上述有效回复音频。另列 SDK EOT 返回/放行时间，避免隐藏意图等待。
- 保留 ASR final、VAD stop、提交、LLM 首段文本、TTS 发文/首包等分段数据。旧播报、被取消的段、空白音频和单纯 thinking 状态不作为新回复。
- 此处测到内存播放端，尚不包含 RTC、设备缓冲和扬声器实际播放。固定延迟的 Mock 回归与真实服务测量分开记录。

### 实测与调整

首轮两例发现，普通接话停声约 0.54 秒后已提交，剩余时间主要在回复模型和 TTS；更正接管另有约 1.43 秒意图等待，之后回复模型首段文本又耗时约 3.07 秒。没有继续压低 VAD/EOT 阈值。

1. 在既有 `_lifecycle_stages` 中为全双工加入有截止时间的无用户数据意图预热。复用同一分类客户端和现有失败处理，结果不进入话轮，也不提前取消播报。half duplex/PTT 不新增分类请求。启动成本移到了会话准备阶段，不是消失了；三个有效更正样本的准备时间约 529/654/765 ms，包含语音阶段预热与 SDK 启动，不能单独归因于意图预热。长时间空闲后仍可能冷连接。
2. `llm.extra_body` 透传既有 LiveKit 适配器的原生参数。配置的 DeepSeek 直连语音回复显式使用非思考模式；意图分类也通过同一工厂设置，删除了分类器里重复的请求参数透传。[供应商文档](https://api-docs.deepseek.com/guides/thinking_mode/)说明默认思考模式开启，可通过 `thinking.type=disabled` 关闭。这涉及回复质量与耗时的取舍，当前验证只覆盖简单语音任务，不是复杂推理质量验收。
3. 检查 SDK 后确认，其预生成入口在当前播报未中断时直接跳过，不能直接消除本次重叠接管的等待，因此保持预生成配置关闭。

| 同一素材场景 | 初始样本（各 1 次） | 调整后中位数（各 3 次） | 调整后范围 |
| --- | --- | --- | --- |

PTT 原用例只记录整段回复结束，已补上松键至首个可听回复的测量，并在整段回复超时时仍保存首音频/提交/输出字节证据。一次补测在 45 秒内未观察到整段回复完成；该次缺少首音频证据，根因未证实，不能用之后通过覆盖。下一次相同输入测得首个可听回复 2710.3 ms、整段完成约 27.3 秒。另发现原测试没有给 PTT 传入其他两模式使用的简短回复指令，已通过既有构造参数对齐，仅修改测试条件，未修改生产 PTT 编排。对齐后真实 PTT 复测通过，松键至首个可听回复 3190.6 ms，整段完成约 4.3 秒；不据此认定之前的超时已经解决。

仍未完成：生产 Agent RPC/RTC/设备端体验验收、真实设备播放背压与长输出打断验证、PTT 超时根因及稳定性、复杂回答质量，以及更广泛真人停顿/口音/噪声覆盖。默认兼容策略的已知语义预期失败仍然存在，本轮不宣称整体任务完成。

## 第十一批：回到完成度误判与说完后的回复延迟（2026-09-06）

## 第十二批：完成度误判的成对验证与现成模型对照（2026-09-06）

## 第十三批：真实语音韵律与现有 SDK 音频完成度对照（2026-09-06）

本轮完成 2 次冒烟、18 次对照回放，复用已安装的 LiveKit 1.7.1 本地音频模型 `v1-mini`，没有安装新依赖或修改 SDK。输入为合成语音 WAV，经真实 Bailian ASR、真实 FireRed pVAD 和生产 channel 回调送入现有测试框架；回复 LLM/TTS 使用脚本，以隔离输入端等待。慢速／快速为保留音高的 0.7×／1.4×；条件句、转问、更正和数字以整句一次 TTS 生成，条件句及转问在原有句间空隙中插入 2.2 秒静音。不是分别合成前后半句再拼接，也不是真人录音。

两组均固定端点等待为 0.25／3 秒、默认意图策略 none。音频组仅在实验进程替换 SDK 的 turn detector，未接回现有文本 `InterruptAwareTurnDetector` 的结算门控；所有输入均没有与旧助手播报重叠，因此**不能据此认定已经支持全双工打断接管**。这是候选接入实验，不能拿模型替换直接覆盖 channel 的主动编排。

| 相同输入条件（每组单次） | 当前文本 EOT | SDK 音频 EOT 实验 |
| --- | --- | --- |
| 慢速完整请求 | 首音频 1300 ms | 3008 ms |
| 快速完整请求 | 780 ms | 2994 ms；ASR final 约 2987 ms 才到 |
| 短答“好” | 1743 ms | 3009 ms |
| 数字“七” | 2411 ms | 3050 ms |
| 更正“不是，我说的是明天” | 731 ms | 3012 ms |

音频组最后一项提交的是“明天我想问的是。”，而 ASR 后续最终文本包含“明天的天气怎么样？”。仅检查“有一条用户消息、有音频、延迟短”会漏掉这一错误。它说明当前实验接入的文本就绪与提交顺序未满足产品契约，不能单凭未抢答或低延迟选用。没有将其归因为已证明的音频模型缺陷。

正常语速条件句前缀音频分数 0.3523，略低于中文阈值 0.355，受到长等待保护；慢速同一句为 0.5590，触发提前回复。完整的慢速请求、“好”“七”、更正句音频分数也低于阈值，走约 3 秒等待。因此本轮**不采用这项直接替换**，不为了通过这些样本另调阈值或加短语规则。

延迟归因也作了纠正：快速完整句的音频预测在停声后约 236 ms 返回且超过阈值，但 ASR final 对应的 channel 更新到约 2987 ms 才出现，回复约 2994 ms。不能把这例称为 SDK 忽略了完整预测、额外等了 3 秒。冒烟中当前方案的一次约 5595 ms 回复同样伴随约 5586 ms 的晚到 final，不能据此声称音频模型更快。每个条件只有一次、服务时延有波动，不是严格性能 A/B 或 P95。模型实际推理约 13–17 ms 也不是用户感知延迟。

测量沿用现有 `ReplyLatencyProbe`，仅允许没有文本预测方法的流式检测器使用同一声学时钟，并给现有时钟测试增加该接口分支。音频实验记录的是预测返回时刻，不能证明 SDK 最终消费哪次预测；原 `final_eot_predictions` 和 `complete_to_reply_audio_ms` 仍是 channel 文本模型的诊断值，不能当作音频模型完成判断。已在[原始证据](voice-validation/phase13-real-audio-endpoint.json)注明。安装版本的 EOT 事件没有对本地 AgentSession 公开发射，本轮没有为获取数据修改 SDK 或增加私有调度 hook。

工程检查继续追踪此前 PTT 识别完成后约 1 秒的等待：`SttStage.recognize_streaming` 在返回前等待 `stream.aclose()`，最终进入 Bailian 连接的 WebSocket 关闭。没有找到该路径上的固定 sleep；本轮没有重新测量 PTT 服务时延，也没有以不受管理的后台关闭掩盖等待。若后续将清理移出回复路径，必须由现有 stage 生命周期接管并验证取消、退出、连续按键下的回收，再作取舍。

## 第十四批：将 PTT 识别收尾移出回复关键路径（2026-09-06）

本轮落实一项已定位的工程优化，生产修改仅在既有 `SttStage`。识别按原有结束边界得到文本后立即交回调用方，关闭流的任务由 stage 持有；下一次整段识别和 `shutdown()` 都等待该任务完成。每个 stage 最多一个待清理流，流式整段识别与离线识别共用同一把锁，防止复用供应商连接时旧任务影响新请求。没有引入连接池、通用后台任务管理器、供应商特例或新超时。

失败／取消的识别仍在传播异常前等待清理；反复取消及取消下一轮等待，不会取消已持有的清理任务。关闭异常有日志，保留原有不覆盖识别错误的行为。生产 PTT 已在 stage 退出前取消并等待 turn tasks，本轮沿用这一顺序；直接调用 stage 的使用方如果不取消识别，`shutdown()` 会等待进行中的识别和清理。

## 第十五批：旧完成边界不能覆盖更长的待定文本（2026-09-06）
