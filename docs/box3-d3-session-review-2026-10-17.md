## 4. 天气慢且失败的完整链路

| 时间（23 点） | 证据 |
|---|---|
| 28:57.939 左右 | Channel 提交天气请求 |
| 28:58.852 | 第一次 get_weather 调用 |
| 29:00.860 | 返回 `eidolon.tool_timeout`；Agent 持久化工具耗时 2001 ms |
| 29:01.401 | 模型第二次请求 get_weather |
| 29:01.407 | `tool_repeat_suppressed`；没有第二次实际外部查询 |
| 29:03.284 左右 | Agent 产出最终失败说明 |
| 29:03.783 左右 | Channel 首音频 |
| 29:03.807 | 首次设备 speaking 回报 |

Agent 本轮约 5339 ms 的输出等待包括：上下文编译 301 ms、triage 13 ms、工具阶段合计 2003 ms、三轮模型流约 594 + 544 + 1872 ms，以及少量调度开销。三轮模型对应“查询→再次尝试查询→生成回答”，不是 Channel 重复提交了三次用户请求。

源码中天气工具总预算默认 2 秒，地理编码和天气查询串行执行；HTTP 客户端 timeout 为 1.5 秒。这与本轮 2001 ms 总超时吻合，但日志没有网络子阶段明细，不能进一步断言是 DNS、TLS、地理编码还是天气请求超时。工具允许未指定城市时使用配置默认城市；本轮工具 trace 未保留参数，不能确定实际使用了哪个城市。

回答承认失败是合理的；“没连上”比实际证据“工具总预算超时”更具体，只能视为不够精确的口语解释。“告诉我城市，我再试一次”可以作为城市澄清，但不能把城市缺失当作已确认的失败原因。

Agent 使用结构化 `eidolon_respond` 输出：完整响应工具参数通过校验后才释放文本。因此底层模型已经收到首个 chunk，并不代表用户已有可播报文本。日志中三个请求的 first model activity 都是 tool_call；笑话、故事并未调用外部业务工具。当前 presentation 模式还排除了普通 slow_tool_hint 路径，本轮也没有等待提示音频。若优化首句输出，需要保留结构化响应校验、表达同步和取消语义，不能直接朗读尚未验证的 JSON 片段。

## 5. 打断与设备播放：用户未听到残音，状态包含保护窗口

| 指标 | 换恐怖故事 | 查天气 | 别说了 |
|---|---:|---:|---:|
| VAD 起说→服务端 duck | 3.6 ms | 4.0 ms | 0.35 ms |
| 起说→最终 playback.stop 记录 | 4670.0 ms | 2339.0 ms | 1565.8 ms |
| 用户讲话持续时间 | 4047.4 ms | 1733.1 ms | 1197.0 ms |
| 语义证据可行动→cancel 完成 | 2.8 ms | 5.3 ms | 1.0 ms |

4.67 秒不是纯“反应迟钝”：包含用户说完 4.05 秒，以及 final/意图收尾。另一方面，服务端 4 ms duck 也不能证明 BOX-3 在 4 ms 停声：已下发的音频仍可能在链路或客户端队列中。

两次换题的设备状态记录如下；这些是控制/保护状态，不是实际声能测量：

| 事件 | 换恐怖故事 | 查天气 |
|---|---|---|
| playback.stop 已发布 | 23:28:46.121 | 23:28:57.902 |
| 设备 idle（收到回报） | 23:28:46.190 | 23:28:57.942 |
| 设备重新 speaking | 23:28:46.232 | 23:28:57.954 |
| 再次 idle | 23:28:47.436 | 23:28:59.198 |
| 新回答服务端首音频 | 23:28:48.277 | 23:29:03.783 |

反跳发生在新回答音频产生之前，并分别持续约 1.20、1.24 秒。用户随后明确反馈没有听到残音。核查客户端源码：`AgentOutputActiveRecently()` 合并 `session_playback_.Active()` 与本地 `PlaybackActiveRecently()`；两者有 1,200 ms 尾部/近期播放窗口。stop 处理先清空本地播放并立即上报 false，后续周期上报仍按组合状态计算。因此，这个序列有状态保护机制上的解释，不能推断播放队列故障。尚未把每条设备回报精确归因于哪个分支，但没有理由据此修改音频控制逻辑。界面由 Channel 状态驱动是合理职责划分；设备同时负责播放执行和本地遥测，并非所有上报都只是服务端状态的原样回显。

第四轮设备在 23:29:11.686 已报 idle，早于 23:29:12.434 发布 stop，因此这一轮不能作为“stop 命令把正在播的声音立即停住”的成功样本；它证明的是 hard_stop 不再触发回答。
