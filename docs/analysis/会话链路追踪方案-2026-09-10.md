# 会话链路追踪方案（Channel Session Trace）

> 状态：待 review（第 2 版）
> 日期：2026-09-10
> 范围：从建立 voice room 到离开 voice room 的全链路时序、每跳耗时与决策证据。
> 只做观测与读取，不做功能入侵。
>
> **本版前提**：`eidolon_admin` 暂不推进，展示以 Mobile 为主。据此本阶段的交付
> 全部收敛在 `eidolon_channel` 仓内；Tier B 只写映射不发布；Mobile 暂不接线。
> 定稿决定见 §5、§6。

## 0. 复盘结论

三句话：

1. **本仓已有三层观测原语，缺的只是一个出口和一个墙钟锚点。**
   `TurnTimeline`（52 marks / 30 segments）、provider 事件桥、`ChannelTurnEventSink`
   都在，但 sink 的 `observer` 恒为 None，事件计数后丢弃；timeline 全是
   `time.monotonic()`，没有任何绝对时间，跨进程无法对齐。
2. **跨系统的历史读取链路已经建成，而且是按 Channel 的事件契约建的。**
   `eidolon_admin` 里有一个只消费 `source == "channel"` 的消费者，
   payload 键名、stage 标签、`RuntimeTurn` 字段逐个对应本仓
   `ChannelTurnEventSink` 的输出。Channel 从来没发过。
3. **但那条链路整条在 admin 仓里** —— 包括 Mobile 直接调用的 `eidolon-local-api`。
   所以本阶段不走它：Channel 侧把信封映射写对、默认关；Tier C 自成闭环。

**不新建**：存储引擎、事件表、索引、第二份读取实现、Mobile 新页面、新 id 体系。

## 2. 三层数据、三个归属（业务边界与逻辑边界）

混层就会造出第二个真相源。

| | Tier A 业务事实 | Tier B 治理/产品可见事件 | Tier C 工程诊断时序 |
|---|---|---|---|
| 内容 | 对话正文、轮次结果、工具调用、记忆命中 | 会话开始/结束/失败、phase 迁移、milestone、终态与耗时 | 52 mark、30 segment、provider 连接细节、决策证据（tier/intent/eot_score/vad） |
| 权威 | **Agent** | **Channel** | **Channel** |
| 落库 | Agent runtime store（已有） | Channel 本地 outbox → JetStream → audit index | Channel 本地 NDJSON |
| 读取 | 已有全链路到 Mobile（`TranscriptView`） | 链路已建成，**但需 3 个 admin 仓进程** | **新增唯一一份**：channel-provider 只读 GET |
| 频率 | 每轮 1 条 | 每轮 ~15–20 条 | 每轮 ~50–150 条 |
| 隐私 | 含正文，Agent 管控 | `safe`：只有 id、phase、耗时、计数 | `safe` + 120 字 preview（既有约定） |
| **本阶段** | 不动 | **只写信封映射，默认不发布** | **主交付** |

**边界铁律：**

- Channel **不复制正文**。ASR 最终文本与 brain 回复已在 Agent 侧落库，并已有到
  Mobile 的统一读取接口。Channel 再存一份就是第二个真相源。
- Tier B **不进 Data、不建全局 events 表**。父仓 `docs/跨系统/权威边界与依赖方向.md`
  已裁决：「不存在一张跨系统全局权威 events 表」「逐帧音频、逐 token 和高频延迟
  属于 telemetry，不应伪装成业务审计」。
- Tier C **不进 audit 流**，留在产生它的 authority 本地、按需拉取。
- Admin 只是**可重建的索引**，不是事实源。
- Channel 独有、别处根本没有的事实：**被拒绝/被打断/未提交的轮次** —— 它们不进
  Agent 的 turn 表（没提交给 brain），而这恰是排查打断与轮次收敛的主要材料。
  这是 Tier B 将来存在的核心理由，也是 Tier C 现在就有价值的理由。

## 3. 本阶段交付：Tier C（全在本仓）

### 3.1 墙钟锚点（唯一的真实数据缺口）

`TurnTimeline` 的 52 个 mark 全是 `time.monotonic()`，`snapshot()` 里没有任何绝对
时间。后果：跨进程（provider / worker / brain / 设备）无法对齐，无法与
`[lifecycle]` 文本日志按时间 join，将来 Tier B 的 `occurred_at` 也无从取。

改法：`TurnTimeline` 增 `clock_anchor: {monotonic, unix_ns}`，`snapshot()` 带出；
sink 侧会话尺度同样存一份。不动任何 `setdefault` 语义。约 8 行。

### 3.2 会话尺度 timeline（room join → leave）

**归属：`BasePipeline`（`shared/pipeline.py:41`），不是 `ChannelTurnEventSink`。**

理由：会话是 session 尺度的事实，与 turn policy 无关，而 `ChannelTurnEventSink`
只存在于 full_duplex —— PTT 管线（`half_duplex/pipeline.py`）完全没有 sink。
把 session trace writer 的开/关放在 `BasePipeline.run()` / `.shutdown()`
（两个管线都已调用 `BasePipeline.shutdown(pipeline)`），可以让 **full_duplex 与 PTT
两种模式都拿到 room join → leave 的会话行**，且 `room_joined` /
`runtime_participant_resolved` 这些发生在 `sink.start(room)`（`lifecycle.py:57`）
之前的 mark 不需要任何预缓冲。

`ChannelTurnEventSink` 留在 full_duplex 不动：turn 尺度的 phase 词汇是全双工特有的，
PTT 有自己的 `ptt_segment` 状态机，强行统一是错的。PTT 的 turn 行照旧写进同一个 writer。

在 `lifecycle.py` 已有 `logger.info` 的位置补 mark：

`room_joined` → `runtime_participant_resolved`（`lifecycle.py:53`）→
`warmup_done`（`:85`）→ `avatar_ready`（`:209`）→ `session_started`（`:104`）→
`first_turn` → `closed(reason)`（`:455`）

这是**必须动产线代码的地方，也是全部**。要绝对零侵入，就只能放弃这几段的耗时。

#### 3.2.1 ⚠️ 打断恢复的三段语义：埋点必须读事件，不能读裁决

`cd070fe` 之后 duck 的恢复是三段，**mixer 不会停在 SUSPENDED**（这一条由
`local_2813e945` 会话在 2026-09-11 纠正，我原先的假设是错的）：

```text
VAD start   → duck，mixer SUSPENDED
VAD stop    → 仍 SUSPENDED，继续压 turn_policy.eot.speech_merge_grace_ms（默认 800ms）
grace 到点  → duck_timeout 发 Action.RESUME
              reason = continuation_grace_elapsed_pending_evidence
              → resume_pending_output() → unduck_if_suspended(drop_buffered=False)
              → mixer NORMAL，orchestrator 进 RESUMED_WAITING_EVIDENCE，candidate 仍 active
再等 post_speech_evidence_timeout_ms（6000ms，从 VAD stop 起算）
            → 终局 verdict expired_resume，continue_to_llm=False，candidate 解除
```

实测（duck 起算）：`SUSPENDED @356ms → NORMAL @1839ms → candidate 解除 @7046ms`。
旁证见 `voice-validation/case-aware-acceptance.json` 的 `recovery_clock_observation`
（`stop_to_recovery_ms=801.2`、`candidate_resolved_elapsed_ms=6701.6`）。

**这两个时刻差约 6 秒，绝不能混用。** 各自的取值来源：

| 要测的东西 | 读哪里 |
|---|---|
| 播放恢复（用户重新听到声音） | `attrs.duck_events[]` 中 `event == "output_resumed_pending_evidence"` 的 `at` |
| candidate 终局（这一轮打断的裁决） | `attrs.interruption_orchestrator_events[]` 的 `candidate_resolved`，或 `attrs.interruption_verdict` |

**用终局裁决当"恢复"就是 `45d5f6e` 修掉的那个 bug**：`benchmark/hil_barge_in.py` 原来
这么读，新契约下读出来是 ~6500ms。`benchmark/timeline_expectations.py` 早就改用
recovery event 了，并留了注释 "Its later terminal verdict cannot stand in for playback"，
只有 HIL 没同步。P0 的 `session_mark` 若要算 duck 恢复耗时，**只读 duck_event 的 `at`**。

另外三个会踩到的细节（同一来源）：

1. **播放空洞的真实上限是 ~6s，不是 2s。** `ducking.buffer_max_ms=2000` 在 owner 持有时
   被绕过（`_resolve_hold_or_rearm` 里 `owner_remaining_sec is not None` 走另一分支）；
   用户持续说话时真正的兜底是 `post_speech_evidence_timeout_ms=6000`，**从起声算**。
2. **用户还在说话时也会 provisional resume**，reason=`active_speech_playback_budget_elapsed`，
   该事件 `user_speaking: true`、`speech_stopped_at: null`。算耗时必须与 stop 后的恢复分开，
   否则会拿 null 去做减法。
3. **turn 尺度的 `timestamps.speech_stopped_at` 会被覆盖。** `_record_duck_event`
   （`full_duplex/interruption_effects.py`）在记录时就快照它，注释写明原因是"后来的声学片段
   会覆盖 timeline 上的 last stop"。会话尺度 mark 不能事后回读这个字段。

这也是 §3.2 把会话 timeline 放在 `BasePipeline`、与 turn 尺度彻底分开的另一个理由：
轮次内的打断裁决有自己的时钟，不该和会话建立阶段共用一套 mark。

### 3.3 出口接线与异步有界写

- 按配置给两处 `ChannelTurnEventSink(...)` 注入 observer（2 行）。所有
  session/phase/milestone/terminal 事件从"计数后丢弃"变成流式落盘，**零新埋点**。
- 现在 `append_debug_jsonl()` 是热路径上的同步 `open/write/close`
  （`pipeline.py:1131`、`:1149`）。Tier C 事件频率高一个量级，必须先异步化：
  `queue.SimpleQueue` + daemon writer 线程，队列满即丢并计数（沿用 `_enqueue`
  的吞异常模式）。现有 JSONL 写入一并挪到同一个 writer。
- 顺带修一个既有问题，**范围限于 full_duplex**：`_flush_turn_timeline` 有
  `_flushed_timeline_ids` 幂等保护，但 `_append_turn_timeline_snapshot`
  （`speech_lifecycle.py:90`、`framework_completed_turn.py:515`、
  `ProviderEventObserver` 回调）没有 —— **同一个 `turn_id` 可能落多行**，而
  `benchmark/timeline.py` 的 ingestion 不去重（只读 `record["turn_id"]`，无 dedupe），
  所以现有 benchmark 百分位可能混入同一轮的多份部分快照。
  PTT 侧不受影响：`_append_ptt_timeline`（`half_duplex/pipeline.py:652`）已有
  `_flushed_timeline_ids` 保护。
  新 writer 按 `turn_id` 收敛为「N 条 progress 行 + 1 条 final 行」并显式标
  `record_kind`，让 ingestion 取 final。

### 3.4 落盘位置与保留（已定，可配置改）

```text
$EIDOLON_STATE_ROOT/channel/traces/<date>/<owner>__<companion>__<runtime_session_id>.ndjson
```

取 `STATE_ROOT` 而非 `LOG_ROOT`：provider 的读接口要读它，而 `LOG_ROOT` 是运维可清
目录。默认 7 天轮转 + 单会话文件大小上限，超限截断并计数。全部走
`ObservabilityConfig`，默认关（dev overlay 开）。

**目录布局即索引，先不建 SQLite。** 触发条件写明：出现"按 phase/耗时跨会话聚合
查询"的真实需求时再加，届时复用 `channel_provider/store.py` 的 schema guard +
迁移审计模式。

### 3.5 读接口 —— 唯一一份实现

仿 `presence` 的写法，在 `eidolon-channel-provider` 上加两个 bearer GET：

```text
GET /v1/session-traces?owner_id=&companion_id=&since=&limit=   → 会话列表(摘要)
GET /v1/session-traces/{runtime_session_id}                     → 单会话完整时序
```

- **实现只有这一份。** 列表 = readdir + 文件名解析；详情 = 读一个文件。
- 任何端接入都走这个 HTTP 契约，不重写解析：CLI / benchmark / 排障脚本直连；
  Admin 用已有 generic proxy 零改动透传；将来 Mobile 由 local-api 加一个**薄投影**
  （只做 owner 鉴权 + 字段裁剪）。
- 离线侧继续用 `benchmark/timeline.py` 的 ingestion，新增
  `scripts/report_session_trace.py` 出瀑布图 —— 直接复用
  `PROVIDER_LATENCY_SEGMENTS` 的 30 个 stage 定义，不另立一套 stage 词汇。

### 3.6 正文（默认关，不进产品链路）

| `occurred_at` | 墙钟 | 由 §3.1 的 `clock_anchor` 换算 |
| `payload` | 已有；`_base_payload()` **必须补 `companion_id`** | 当前只有 `room_name`+`device_id`；Admin `_event()` 从 `payload["companion_id"]` 取，缺了这轮就不属于任何 Companion |

### 4.2 将来要发哪些事件

Admin 的 `_channel_turn_stages()`（`service.py:1329`）用
`phase_changed.payload["phase"]` + `milestone.payload["milestone"]` + `elapsed_ms`
构造 stage 序列 —— 所以 phase 和 milestone **都得发**，只发终态则 Mobile 上的轮次
没有 stage 分解。即 `ChannelTurnEventSink` 现在已产生的全部，一条不多。

### 4.3 契约陷阱清单（先记下，打开开关前逐条清）

1. **`owner_id` 缺失** → audit index owner 分片查不到。§4.1。
2. **`data_classification` 漂移**：SDK 契约是 `safe|sensitive|restricted`
   （`envelope.schema.json:37`），Admin 的 Python `PrivacyMode` 是
   `safe|summary|restricted`（`app/mission_control/schemas.py:27`）。发 `sensitive`
   会让 Admin 的 pydantic 投影直接失败。Channel 只发 `safe` 可绕开；漂移本身是
   admin 侧既有 bug（§6.3）。
3. **`severity` 收窄**：信封允许 `critical`，Admin `RuntimeSeverity` 只有
   `info|warn|error`。不发 `critical`。
4. **`companion_id` 缺失** → 轮次不归属任何 Companion。§4.1。
5. **`producer_seq` 必填且单调**：Mission Control 用它检测单 producer 序列缺口。
   worker 是多进程并发的，必须单点分配。

### 4.4 本阶段范围

写：映射模块 + 上面 4 个必补字段 + 一个默认 `off` 的开关。
不写：outbox、dispatcher、JetStream 发布、任何 admin 侧改动。
`nats-py` **不进本仓依赖**。

### 未定（等 P3 再决，已调研，勿重复）

**6.1 outbox 形态。** worker 是 LiveKit 每 job spawn 的短命进程，没有自己的业务
数据库，不能在热路径做 NATS 往返，所以 Data/Agent 的"业务事务内落 outbox"不适用。

- **A. spool 目录 + provider 发布（倾向）**：worker 只 append
  `$EIDOLON_STATE_ROOT/channel/audit-spool/<session>.ndjson`；常驻 provider 扫描、
  按信封发布、成功即删，`producer_seq` 由 provider 单点分配。热路径只有一次文件
  append，worker 无 NATS 依赖，崩溃不丢已写事件。代价：多一个扫描环节、投递延迟。
- **B. worker 直连 JetStream**：无中间环节；但依赖进 worker、每 job 建连、
  worker 被 kill 时未发出的事件全丢 —— 而"被 kill"正是最需要事件的场景。
- **C. worker → provider loopback POST → provider outbox SQLite**：语义最接近
  Data/Agent；但热路径引入本地 HTTP 往返和一个新失败模式。

**6.2 Mobile 的展示形态。** 两条路，本阶段都不做：

- 历史视图：必须过 `eidolon-local-api`（admin 仓）。Channel 侧零额外工作。
- 实时视图：LiveKit 数据通道，零 admin、零存储、零新服务；只有当次会话，
  且要动 SDK wire 契约（topic 常量 + envelope + mobile/esp32 contract mirror）。

**6.3 admin 侧待修（记录，不在本仓）。**

- audit index 无任何保留/清理策略，而 Tier B 是每轮 15–20 条。打开发布前必须先
  给它加保留期，否则会无界增长。**这是本方案唯一会影响别人磁盘的地方。**
- `PrivacyMode` 与 SDK `data_classification` 契约漂移（§4.3 陷阱 2）。
